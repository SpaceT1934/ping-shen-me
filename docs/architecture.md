# 工程架构

本工程将网页展示、业务规则、HTTP 处理和持久化分开。前端不能直接访问数据库；状态变更必须经过后端校验和事务。

## 数据流

页面组件 → GardenProvider → garden-api → 路由 → GardenService → domain 规则 → Repository 事务 → PostgreSQL。

后端返回完整已提交快照，前端更新 TanStack Query 缓存。页面之间读取同一缓存，不分别维护成长、任务或成果副本。Provider 只协调请求和错误显示，不实现目标完成、成果生成等业务规则。

## 层的职责

| 层           | 路径                      | 职责                                         |
| ------------ | ------------------------- | -------------------------------------------- |
| 接口契约     | packages/contracts        | Zod 输入、响应及持久化结构定义               |
| 业务领域     | packages/domain           | 纯函数执行命令、成长阶段、成果判定、报告计算 |
| 前端页面     | apps/web/src/features     | 表单和交互，展示成功保存的数据               |
| 前端数据访问 | apps/web/src/lib/garden   | HTTP、旧缓存迁移、视图映射                   |
| 后端路由     | apps/api/src/modules      | 参数校验、会话上下文、响应                   |
| 应用服务     | garden.service.ts         | 组合领域逻辑与事务，生成提交指纹             |
| 数据访问     | apps/api/src/repositories | 会话查询、快照读写、数据库生命周期           |

项目详情按目标、任务、记录、成果、设置拆成组件。纯业务层不导入 React、Fastify、数据库客户端或浏览器 API。

## 持久化方式

当前手动 V1 用 `users`、`web_sessions`、`garden_snapshots` 保存身份、会话和每用户聚合数据。聚合中包含项目、目标、任务、记录、成长事件、进度事件和成果。一次任务完成涉及多个对象，因此统一在一个事务内保存快照，避免部分成功。

仓库使用 `SELECT ... FOR UPDATE` 锁定用户花园，执行纯函数后整体写入 JSONB。请求中的 `expectedVersion` 防止旧页面覆盖新数据；`operationId` 和指纹防止同一请求因重试重复产生行动或成果。保留最近 500 次幂等记录，超出窗口的旧请求也会被版本检查拒绝。

早期骨架中的实体表仍保留在迁移历史里，目前不写入它们，不同时维护第二套事实。后续需要全库分析或大规模分页时，可以在 Repository 层实现实体表投影或存储迁移，不修改页面和领域规则。

默认开发驱动为 PGlite，数据保存在后端本地目录；生产使用独立 PostgreSQL。两个驱动使用相同 Drizzle SQL 迁移和仓库操作。启动时执行迁移，失败则不接受业务请求。

## 用户与安全边界

匿名会话使用高强度随机 Cookie，服务端只保存令牌哈希，Cookie 为 HttpOnly、SameSite=Lax，生产环境设置 Secure。业务请求从 Cookie 获取用户，不接受客户端指定用户 ID。用户只能读写自己的快照。跨站写请求的 Origin 会被校验。

身份方式符合当前测试链接阶段，手机号和第三方登录尚未接入，不能视为正式账号系统或跨设备恢复方案。

## 输入恢复和迁移

文字草稿与手动确认卡片暂存 sessionStorage，刷新或网络失败不会清空输入。成功后才清空草稿、播放反馈。匿名会话首次加载时，若服务端花园为空，可一次性导入旧版 localStorage；旧缓存保留，不覆盖已经有数据的服务端花园。

## 扩展边界

本轮没有 AI、语音供应商或密钥。未来 AI 只产出手动确认卡片同样的 Draft，由用户确认后调用现有命令入口，不直接改数据库或判断成果。正式账号服务可以替换会话解析入口，业务服务仍只接受服务端确认的用户身份。
